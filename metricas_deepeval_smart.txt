METRICAS DO DEEPEVAL NO PROJETO SMART

Este projeto usa tres metricas principais para avaliar a API SMART:

1. G-Eval
2. Tool Correctness
3. Task Completion

Cada metrica gera linhas no CSV de metricas com campos como:

- numero
- metric_name
- score
- threshold
- passed
- reason
- question
- actual_output
- expected_output
- route
- agents_called
- tools_called
- expected_tools
- tools_correct
- tools_missing
- tools_extra


1. G-EVAL

O que mede:
Avalia a qualidade tecnica da resposta final da API SMART.

Pergunta que responde:
"A resposta foi boa, correta, clara, fundamentada e util para o usuario?"

Como funciona:
O G-Eval compara:

- input: pergunta do usuario
- actual_output: resposta real da API SMART
- expected_output: resposta esperada do db.json usada como referencia tecnica

No projeto SMART, o G-Eval foi configurado para nao punir automaticamente diferencas numericas quando a API estiver usando dados atuais coletados por sensores ou provedores externos. O foco e avaliar se a conclusao, recomendacao, justificativa tecnica e uso dos dados fazem sentido.

Campos importantes:

- score: nota de 0 a 1.
- threshold: meta minima para passar, normalmente 0.7.
- passed: true se score >= threshold.
- reason: explicacao textual do juiz sobre por que deu aquela nota.

Interpretacao:

- score alto: resposta tecnicamente boa, direta, fundamentada e util.
- score baixo: resposta vaga, incompleta, incoerente, sem conclusao clara ou desalinhada dos criterios tecnicos esperados.


2. TOOL CORRECTNESS

O que mede:
Avalia se a API SMART chamou as ferramentas corretas para responder a pergunta.

Pergunta que responde:
"A API chamou as tools certas?"

Como funciona:
Compara:

- tools_called: tools realmente chamadas pela API SMART.
- expected_tools: tools esperadas para aquele tipo de pergunta.

Campos importantes:

- score: nota de 0 a 1 sobre acerto das tools.
- passed: true se score >= threshold.
- reason: explicacao textual do que faltou ou sobrou.
- tools_correct: tools esperadas que foram chamadas corretamente.
- tools_missing: tools que deveriam ter sido chamadas e nao foram.
- tools_extra: tools chamadas sem necessidade.

Interpretacao:

- score 1.00: chamadas de tools corretas.
- score intermediario: parte das tools certas foi chamada, mas faltou algo ou houve excesso.
- score baixo: a API escolheu tools inadequadas ou deixou de chamar tools essenciais.

Exemplo:
Se a pergunta pede temperatura, umidade e vento, mas a API chama apenas vento e solo, o Tool Correctness deve cair porque faltaram ferramentas de ar.


3. TASK COMPLETION

O que mede:
Avalia se a tarefa foi concluida de ponta a ponta.

Pergunta que responde:
"A API resolveu a tarefa do usuario de forma completa?"

Como funciona:
Avalia a execucao observada no fluxo:

- pergunta do usuario
- chamada da API SMART
- resposta final
- resultado esperado

No projeto SMART, essa metrica roda via tracing/observed agent, entao pode ser mais pesada e mais lenta que as outras.

Campos importantes:

- score: nota de 0 a 1 sobre conclusao da tarefa.
- passed: true se score >= threshold.
- reason: explicacao sobre o que foi ou nao concluido.
- actual_output: resposta observada.
- expected_output: referencia esperada.

Interpretacao:

- score alto: tarefa resolvida de forma completa e util.
- score baixo: tarefa incompleta, resposta parcial, falta de decisao, falta de dado essencial ou recomendacao insuficiente.


COMO INTERPRETAR AS TRES JUNTAS

G-Eval alto + Tool Correctness alto + Task Completion alto:
A API SMART respondeu bem, usou as tools corretas e concluiu a tarefa.

G-Eval alto + Tool Correctness baixo:
A resposta pode parecer boa, mas o caminho de ferramentas foi incompleto ou inadequado.

Tool Correctness alto + G-Eval baixo:
A API chamou as tools certas, mas interpretou mal os dados ou respondeu de forma ruim.

Task Completion baixo:
Mesmo com alguma resposta ou tool correta, a tarefa final nao foi resolvida de forma satisfatoria.


RESUMO

G-Eval:
Mede qualidade tecnica da resposta.

Tool Correctness:
Mede uso correto das ferramentas.

Task Completion:
Mede conclusao da tarefa de ponta a ponta.

Essas metricas se complementam. Uma resposta pode passar em uma e falhar em outra, e isso ajuda a identificar se o problema esta na resposta final, na selecao de ferramentas ou na execucao completa da tarefa.


O QUE CADA FERRAMENTA DE AVALIACAO FAZ E NAO FAZ


1. G-EVAL

O que faz:

- Avalia a qualidade tecnica da resposta final.
- Verifica se a resposta atende ao objetivo central da pergunta.
- Analisa se ha conclusao explicita quando a pergunta exige decisao.
- Considera se a recomendacao e acionavel e tecnicamente justificada.
- Usa o expected_output como referencia tecnica, nao como copia literal obrigatoria.
- Permite avaliar respostas dinamicas geradas com dados atuais da API SMART.

O que nao faz:

- Nao verifica diretamente se as tools corretas foram chamadas.
- Nao garante que os dados retornados pelos sensores estejam corretos na origem.
- Nao deve exigir igualdade numerica literal com o db.json quando a API usa dados atuais.
- Nao substitui revisao agronomica humana em decisoes de campo reais.

Utilidade na avaliacao:

- Mede se a resposta final e util para o usuario.
- Ajuda a avaliar qualidade de raciocinio, conclusao e recomendacao.
- E mais adequada que uma comparacao rigida quando os dados sao dinamicos.
- Ajuda a detectar respostas vagas, contraditorias ou sem decisao clara.

O que justifica o uso:

A API SMART responde com dados em tempo real ou dados atuais vindos de sensores, OpenWeather, InfluxDB, RAG e agentes especializados. Como esses valores mudam, uma metrica rigida baseada em igualdade com o expected_output pode punir respostas corretas. O G-Eval permite julgar a coerencia tecnica da resposta mesmo quando os numeros atuais diferem da referencia do db.json.


2. TOOL CORRECTNESS

O que faz:

- Avalia se a API SMART chamou as ferramentas esperadas.
- Compara tools_called com expected_tools.
- Identifica tools corretas, faltantes e extras.
- Mede a qualidade da selecao de ferramentas pelo orquestrador.
- Ajuda a descobrir se a resposta foi baseada nas fontes/agentes certos.

O que nao faz:

- Nao avalia se o texto final ficou bom.
- Nao julga se a recomendacao final foi tecnicamente bem escrita.
- Nao garante que o dado retornado por uma tool esteja correto.
- Nao mede se o usuario ficou satisfeito com a resposta.
- Nao substitui G-Eval ou Task Completion.

Utilidade na avaliacao:

- Mostra se o problema esta no roteamento dos agentes/tools.
- Ajuda a ajustar o ai.orchestrate.ts ou a logica de selecao de agentes.
- Permite diagnosticar falhas como ausencia de tools de ar, chuva, vento, solo ou radiacao.
- E essencial para avaliar uma arquitetura agentic, onde o caminho de execucao importa.

O que justifica o uso:

O projeto SMART nao e apenas um chatbot textual. Ele possui agentes e tools especializadas para consultar solo, ar, chuva, vento, radiacao e outros dados. Por isso, nao basta a resposta parecer boa: ela precisa ter usado as ferramentas corretas para sustentar a conclusao. Tool Correctness mede exatamente essa aderencia entre pergunta, ferramentas esperadas e ferramentas realmente chamadas.


3. TASK COMPLETION

O que faz:

- Avalia se a tarefa foi concluida de ponta a ponta.
- Considera o fluxo completo entre pergunta, execucao da API e resposta final.
- Mede se o usuario recebeu uma resposta funcional para o objetivo pedido.
- Usa tracing/observed agent para avaliar a execucao observada.
- Ajuda a validar o comportamento geral do sistema, nao apenas um trecho isolado.

O que nao faz:

- Nao e a melhor metrica para diagnosticar qual tool especifica faltou.
- Nao substitui Tool Correctness na analise de ferramentas.
- Nao substitui G-Eval na analise fina da qualidade tecnica da resposta.
- Pode ser mais lenta e mais sensivel a timeout, pois reexecuta parte do fluxo.

Utilidade na avaliacao:

- Mede se o sistema realmente resolveu a tarefa.
- Ajuda a detectar respostas parciais ou execucoes incompletas.
- E util para avaliar o comportamento final do SMART como produto.
- Complementa G-Eval e Tool Correctness ao olhar a tarefa inteira.

O que justifica o uso:

Mesmo que a API chame as tools certas e produza uma resposta tecnicamente razoavel, ainda e necessario saber se a tarefa do usuario foi efetivamente concluida. Task Completion avalia esse fechamento de ponta a ponta. No SMART, isso e importante porque muitas perguntas exigem decisao agronomica, avaliacao de risco e recomendacao pratica, nao apenas listagem de dados.


POR QUE USAR AS TRES JUNTAS

Nenhuma das tres metricas sozinha cobre todo o comportamento esperado da API SMART.

- G-Eval avalia a qualidade tecnica da resposta.
- Tool Correctness avalia se o sistema buscou os dados certos.
- Task Completion avalia se a tarefa foi concluida.

Juntas, elas permitem separar tres tipos de problema:

1. Problema de resposta final:
A API ate chamou dados corretos, mas respondeu mal. Isso aparece em G-Eval.

2. Problema de orquestracao:
A resposta pode parecer boa, mas faltaram tools importantes. Isso aparece em Tool Correctness.

3. Problema de execucao completa:
O sistema ate tentou responder, mas nao concluiu bem a tarefa. Isso aparece em Task Completion.

Essa combinacao e justificada porque o SMART e uma API agentic com orquestrador, agentes especializados, tools tecnicas e resposta final em linguagem natural. Avaliar apenas texto seria insuficiente; avaliar apenas tools tambem seria incompleto.
